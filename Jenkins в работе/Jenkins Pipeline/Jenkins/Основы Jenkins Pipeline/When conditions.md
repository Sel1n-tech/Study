### Что такое when

Представьте, что у вас есть пайплайн, который деплоит приложение. Логично, что деплой в продакшен должен происходить только из определённой ветки (например, main), а не из любой feature-ветки разработчика. Именно для таких ситуаций существует директива `when`.

Директива `when` добавляется внутрь стейджа и определяет условие его выполнения. Если условие не выполняется, стейдж просто пропускается — без ошибки, без остановки пайплайна. Jenkins помечает такой стейдж как "Skipped" (пропущен) и переходит к следующему.

Это решает несколько задач:

- Безопасность: деплой в продакшен только из проверенных веток
- Эффективность: не запускать тяжёлые тесты, если код не изменился
- Гибкость: запускать определённые шаги только по расписанию или вручную
- Логика: выполнять действия в зависимости от параметров билда

Важное отличие от обычной ошибки: если условие не выполнено, пайплайн НЕ падает. Стейдж просто пропускается, и выполнение продолжается.

### Минимальный пример

```typescript
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                echo 'Building application...'
            }
        }

        stage('Deploy') {
            when {
                branch 'main'
            }
            steps {
                echo 'Deploying to production...'
            }
        }
    }
}
```

Что здесь происходит:

- `when { branch 'main' }` — условие выполнения стейджа Deploy
- Стейдж Deploy запустится только если пайплайн работает в ветке main
- Для веток develop, feature/login, hotfix/bug — стейдж будет пропущен
- Стейдж Build выполняется всегда, так как у него нет условия `when`

Визуализация процесса:

```yaml
Ветка main:           Ветка feature/new:
Build → Deploy        Build → [Deploy пропущен]
   ✓       ✓             ✓           ⊘
```

### Как Jenkins проверяет условия

Когда пайплайн доходит до стейджа с `when`, Jenkins останавливается и проверяет условие. Проверка происходит ДО того, как стейдж начнёт выполняться, поэтому никакие ресурсы не тратятся впустую.

Процесс выглядит так:

```csharp
1. Пайплайн доходит до стейджа с when
   ↓
2. Jenkins вычисляет условие (true или false)
   ↓
3а. Если true → стейдж выполняется
   ↓
3. Переход к следующему стейджу

3б. Если false → стейдж помечается как Skipped
   ↓
4. Переход к следующему стейджу (без ошибки)
```

Это значит, что можно смело добавлять условия в стейджи — они не сломают пайплайн, а просто управляют потоком выполнения.

### Основные типы условий

Jenkins предоставляет несколько встроенных типов условий. Рассмотрим самые важные:

**1. Проверка ветки (branch)**

Проверяет имя текущей ветки Git. Это самое частое использование `when`.

```csharp
when {
    branch 'main'
}
```

Условие сработает только если пайплайн запущен из ветки main. Для всех остальных веток — стейдж пропустится.

**2. Проверка переменной окружения (environment)**

Проверяет значение переменной окружения.

```csharp
when {
    environment name: 'DEPLOY_ENV', value: 'production'
}
```

Стейдж выполнится, только если переменная DEPLOY_ENV равна 'production'.

**3. Проверка изменений в файлах (changeset)**

Проверяет, были ли изменения в определённых файлах или директориях.

```csharp
when {
    changeset "frontend/**"
}
```

Стейдж запустится только если в текущем коммите изменились файлы в директории frontend.

### Паттерны для веток

Иногда нужно проверить не конкретное имя ветки, а паттерн. Например, все ветки, начинающиеся с release/. Для этого используется регулярное выражение:

```javascript
stage('Deploy to Staging') {
    when {
        branch pattern: "release/.*", comparator: "REGEXP"
    }
    steps {
        echo 'Deploying release branch to staging'
    }
}
```

Здесь:

- `pattern: "release/.*"` — регулярное выражение, где .* означает "любые символы"
- `comparator: "REGEXP"` — указывает использовать регулярные выражения
- Условие сработает для release/1.0, release/2.5, release/hotfix и т.д.

### Использование expression для сложной логики

Когда встроенных условий недостаточно, можно написать произвольное Groovy-выражение с помощью `expression`:

```javascript
stage('Night Deployment') {
    when {
        expression {
            def hour = new Date().hours
            return hour >= 22 || hour <= 6
        }
    }
    steps {
        echo 'Deploying during night hours'
    }
}
```

Разберём этот пример:

- `new Date()` — получаем текущую дату и время
- `.hours` — извлекаем час (от 0 до 23)
- `hour >= 22 || hour <= 6` — проверяем, что сейчас либо после 22:00, либо до 6:00
- `return` — возвращаем true (выполнить) или false (пропустить)

Блок `expression` может содержать любую Groovy-логику: проверку переменных, чтение файлов, вызов внешних API.

### Практический пример: многоокружение

Рассмотрим реальный сценарий: у нас три окружения (dev, staging, production), и для каждого свои правила деплоя.

```typescript
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'make build'
            }
        }

        stage('Deploy to Dev') {
            when {
                not { branch 'main' }
            }
            steps {
                sh 'deploy.sh dev'
            }
        }

        stage('Deploy to Staging') {
            when {
                branch 'develop'
            }
            steps {
                sh 'deploy.sh staging'
            }
        }

        stage('Deploy to Production') {
            when {
                allOf {
                    branch 'main'
                    environment name: 'PROD_APPROVED', value: 'true'
                }
            }
            steps {
                sh 'deploy.sh prod'
            }
        }
    }
}
```

Логика этого пайплайна:

- **Build** выполняется для всех веток — нет условий
- **Dev** — для всех веток кроме main (разработчики тестируют свои ветки)
- **Staging** — только для ветки develop (интеграционное окружение)
- **Production** — только для main и только если есть подтверждение (переменная PROD_APPROVED)

Схема выполнения для разных веток:

```bash
feature/login:    develop:          main (approved):
Build  ✓          Build  ✓          Build  ✓
Dev    ✓          Dev    ⊘          Dev    ⊘
Staging ⊘         Staging ✓         Staging ⊘
Prod   ⊘          Prod   ⊘          Prod   ✓
```

### Опция beforeAgent

По умолчанию Jenkins сначала выделяет агента для стейджа, а потом проверяет условие `when`. Это может быть неэффективно, если агенты — дорогой ресурс.

Опция `beforeAgent true` меняет порядок: сначала проверка условия, потом выделение агента.

```javascript
stage('Production Deploy') {
    agent {
        label 'production-server'
    }
    when {
        beforeAgent true
        branch 'main'
    }
    steps {
        echo 'Deploying'
    }
}
```

Процесс с `beforeAgent true`:

```1c
1. Проверить условие when
   ↓
2а. Если false → пропустить (агент НЕ используется)

2б. Если true → выделить агента
   ↓
3. Выполнить стейдж
```

Это экономит ресурсы: если условие не выполнено, дорогой production-сервер вообще не задействуется.
