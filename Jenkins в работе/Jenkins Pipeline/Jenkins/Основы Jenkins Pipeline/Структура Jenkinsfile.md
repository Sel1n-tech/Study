### Что такое Jenkinsfile

Jenkinsfile — это текстовый файл, в котором описан весь процесс CI/CD вашего проекта. Он живёт в репозитории рядом с кодом и содержит инструкции, как собрать, протестировать и задеплоить приложение.

Jenkinsfile пишется на языке Groovy и использует специальный синтаксис Jenkins Pipeline DSL (Domain Specific Language). Есть два типа синтаксиса: **Declarative Pipeline** (декларативный) и **Scripted Pipeline** (скриптовый). В курсе мы будем использовать Declarative Pipeline, так как он проще и покрывает большинство задач.

Jenkinsfile размещается в корне репозитория и имеет стандартное имя `Jenkinsfile` без расширения.

```perl
my-project/
├── src/
├── tests/
├── Jenkinsfile          # Описание пайплайна
└── README.md
```

### Минимальный пример

```typescript
pipeline {
    agent any
    stages {
        stage('Hello') {
            steps {
                echo 'Hello World'
            }
        }
    }
}
```

Что здесь происходит:

- `pipeline { }` — обязательный блок, который оборачивает весь пайплайн
- `agent any` — указывает, что пайплайн может выполняться на любом доступном агенте
- `stages { }` — блок, который содержит все стейджи пайплайна
- `stage('Hello') { }` — один стейдж с названием "Hello"
- `steps { }` — блок с шагами, которые выполняются внутри стейджа
- `echo 'Hello World'` — команда для вывода текста в консоль

### Анатомия Jenkinsfile

Давайте разберём структуру более подробно и посмотрим на расширенный пример:

```typescript
pipeline {
    // 1. Определение агента для всего пайплайна
    agent any

    // 2. Блок со стейджами
    stages {
        stage('Build') {
            steps {
                echo 'Building application...'
            }
        }

        stage('Test') {
            steps {
                echo 'Running tests...'
            }
        }

        stage('Deploy') {
            steps {
                echo 'Deploying application...'
            }
        }
    }
}
```

Основные элементы структуры:

1. **pipeline** — корневой блок, обязательный элемент любого декларативного пайплайна
2. **agent** — определяет, где будет выполняться пайплайн (на каком агенте или ноде)
3. **stages** — контейнер для всех стейджей, должен содержать хотя бы один стейдж
4. **stage** — логическая единица работы с понятным названием (сборка, тестирование, деплой)
5. **steps** — конкретные команды и действия, которые выполняются в рамках стейджа

### Более реалистичный пример

Рассмотрим пайплайн для типичного Node.js приложения:

```typescript
pipeline {
    agent any

    stages {
        stage('Checkout') {
            steps {
                // Получаем код из репозитория
                git 'https://github.com/mycompany/myapp.git'
            }
        }

        stage('Install Dependencies') {
            steps {
                // Устанавливаем зависимости проекта
                sh 'npm install'
            }
        }

        stage('Test') {
            steps {
                // Запускаем тесты
                sh 'npm test'
            }
        }

        stage('Build') {
            steps {
                // Собираем приложение для продакшена
                sh 'npm run build'
            }
        }
    }
}
```

В этом примере мы видим реальную последовательность работы:

- **Checkout** — получение кода из Git-репозитория через команду `git`
- **Install Dependencies** — установка npm-пакетов командой `sh 'npm install'`
- **Test** — запуск тестов через `npm test`
- **Build** — создание production-сборки приложения

Команда `sh` используется для выполнения shell-команд на Linux/Unix системах. Для Windows используется `bat` или `powershell`.

### Важные детали

Jenkinsfile чувствителен к регистру и структуре. Обязательные требования:

- Файл должен начинаться с блока `pipeline { }`
- Внутри `pipeline` обязательно должен быть `agent`
- Блок `stages` должен содержать как минимум один `stage`
- Каждый `stage` должен иметь блок `steps`
- Внутри `steps` должна быть хотя бы одна команда

Если нарушить эту структуру, Jenkins выдаст ошибку валидации ещё до запуска пайплайна.

### Визуальное представление структуры

```scss
pipeline                    ← Корневой блок
│
├── agent                   ← Где выполнять
│
└── stages                  ← Контейнер стадий
    │
    ├── stage('Name 1')     ← Первый стейдж
    │   └── steps           ← Шаги первого стейджа
    │       ├── команда 1
    │       └── команда 2
    │
    ├── stage('Name 2')     ← Второй стейдж
    │   └── steps           ← Шаги второго стейджа
    │       └── команда 3
    │
    └── stage('Name 3')     ← Третий стейдж
        └── steps           ← Шаги третьего стейджа
            └── команда 4
```

Эта структура повторяется в каждом Jenkinsfile. Все остальные элементы (о которых мы узнаем позже) будут дополнять эту основу, но базовая иерархия останется неизменной.
